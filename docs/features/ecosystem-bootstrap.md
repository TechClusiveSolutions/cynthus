# Ecosystem bootstrap (one command to build, run, test and remove the Cynthus stack)

Type: infrastructure (developer tool). Repository: cynthus-tools. Tracking issue: cynthus#84.
Approved by the owner 2026-11-15 with three additions (D5 to D7).

## Intent (binding)

Owner, 2026-11-15: "a Makefile style script that can build and tear down the Cynthus ecosystem on a new or existing machine", with these commands, kept as stated: install-prereqs (git, python and libs, docker and compose), build (clone the repos into a specified location), rebuild (rebuild all images and recreate the containers from them), configure (build the .env files with sensible defaults), run (start all services in the correct order), install (install-prereqs, build, configure, run), test (the full unit suite), test-full (unit and integration), test-all (unit, integration and axe), stop (stop all containers), tear-down (`docker compose down` in each repo with services), remove (stop everything, delete containers and images, remove the cloned repos).

Problem: today a new host needs the manual steps of `docs/infrastructure.md` (first-time setup: network, clones, one hand-made `.env` per repo from six READMEs, start order, health checks), and no single command runs the tests across repos. Approach (owner's): one Makefile-style script with the twelve commands above.

## Decisions (owner)

- D1 (2026-11-15). Placement: cynthus-tools (private). Consequence accepted: a bare machine must already have git, an SSH key and the `gh-btm` alias to fetch the script; `install-prereqs` then runs from the clone. The README says so as step 1.
- D2 (2026-11-15). Platforms in the first version: Debian and Ubuntu Linux only (apt, native Docker). macOS with Colima and Windows with WSL2 are later.
- D3 (2026-11-15). Access: SSH key and the `gh-btm` alias, as the machines are set up today. The script checks that the alias works and stops with instructions when it does not.
- D4 (2026-11-15). `test-all` waits for the live axe audit: it is built last, after cynthus-tools#1 to #4.
- D5 (2026-11-15). The base image: if the private repositories clone, the base image can be pulled (owner's statement). The script pulls `ghcr.io/techclusivesolutions/cynthus-base:main` and does not build a fallback; a refused pull stops with the Docker message and exit 2. The first live run (AC11) confirms it.
- D6 (2026-11-15). `--accept-all` answers yes to every prompt. Two ways to run an install: fully automated (`--accept-all`) and confirm by stage (the default for `install`).
- D7 (2026-11-15). `--bus-backend azure` makes Azure Service Bus the broker, and only Auth, API, Worker, Scheduler, Analysis, Chat and Domain get bus connections.

## Assumptions (confirm or change)

- A1. Name and form: the command is `cynthus-env` (shell entry point `bin/cynthus-env`, logic in a Python package `cynthus_env/`), plus a thin `Makefile` so `make build` and `make test` work as well. Python 3 and git are present on Debian 12; `install-prereqs` installs the rest.
- A2. Layout: `--root DIR` (default `~/cynthus`) holds one folder per repository, named like the GitHub repository (not like the owner's current local names). The script never touches the owner's existing development tree unless `--root` points at it.
- A3. Repository list and roles live in one manifest, `cynthus_env/stack.json` (name, GitHub name, role: service, library, test, docs, tool; compose directory; start order; test commands). Adding a repository means editing the manifest only. Branch to clone and update: `dev`; updates are `git pull --ff-only` and never discard local work.
- A4. Start order (from F5, as data in the manifest): create `cynthus_net` if missing, emulators (mail, messaging, rabbitmq), trust, core, intelligence, health; mocks only with `run --with-mocks`. Each stage waits until every container of the stage is healthy (default timeout 300 s per stage, configurable) and stops with the failing container's name and last log lines. `run` is idempotent.
- A5. (default backend `rabbitmq`, see A18) `configure` writes one `.env` per service repository from a template in `cynthus_env/templates/`, with generated secrets (random passwords, the Auth JWT key) kept in `<root>/.cynthus/secrets.env` (mode 600, outside every repository) so a second `configure` reuses them. Defaults: `SIGNAL_BROKER=rabbitmq` everywhere with the matching `RABBITMQ_URL`; `AUTH_SEED_TEST_USER=true`; `LLM_PROVIDER=fake`; distinct subnets per segment; `TIME_ZONE=UTC`. An existing `.env` is never overwritten without `--force`; a diff of what would change is shown.
- A6 (revised by D5). Images: `build` and `rebuild` pull `ghcr.io/techclusivesolutions/cynthus-base:main`; a refused pull stops with the Docker message and exit 2 (no fallback).
- A7. `stop` is `docker compose stop` per repository, in reverse order. `tear-down` is `docker compose down` per repository, in reverse order, never with `-v` (data volumes survive). `remove` is the only command that deletes volumes, images and clones.
- A8. `remove` safety: it lists what it will delete and asks for a typed confirmation (answered by `--accept-all`, A16); it refuses a root that is not under the given `--root`, a root that is a home folder or `/`, and any clone with uncommitted changes or unpushed commits unless `--force`. It removes only containers, images and volumes whose compose project belongs to the manifest.
- A9. `test` runs unit tests for every repository in the manifest that has them: Python per container as in F7 (a virtual environment per repository under `<root>/.cynthus/venv/`, cynthus-shared cloned and put on `PYTHONPATH`), Node tests for the core web container (Node 22, installed by `install-prereqs`). It does not need the stack to be running. The commands per repository are in the manifest, taken from each CI `test` job; a drift test compares them (see AC8).
- A10. `test-full` adds the feature integration tests (core `tests/integration/workflow`, and `workflow_database` against the running core database from a container on the network) and the system integration suite (`cynthus-testing`, run against the running stack with the seeded test user). It starts the stack with `run` if it is not running and says so.
- A11. `test-all` adds the live axe audit once it exists (cynthus-tools#1 to #4). Until then the command is present and reports "axe audit not built yet" with exit code 2, not 0.
- A12. Output: every command prints each step, exits 0 only when every step succeeded, 1 for failed checks (tests), 2 for failures to run (missing prerequisite, timeout). `--dry-run` prints the commands without running them. A log of each run goes to `<root>/.cynthus/logs/`.
- A13. Board values: tracking issue XL (Feature), Priority P2, milestone "Cynthus 1.0 - Platform Foundation Complete", Status Planned, due date today plus 3 days; slice sizes below. cynthus-tools has no milestone, so its issues are filed without one as for the axe audit plan; slice issues in cynthus-testing and cynthus use the milestone.
- A14. cynthus-tools#1 (axe stack lifecycle) is to be built on `run`, `stop` and `tear-down` of this script once S3 is merged, instead of duplicating compose handling. I will add a comment on that issue when this plan is published; order of the two plans: bootstrap S1 to S4 before axe S0.
- A16. `--accept-all` (global option, replaces `--yes`): every yes/no prompt is answered yes without reading input. It does not answer the safety refusals of A8 (root checks, dirty or unpushed clones): those still need `--force`, which is separate and never implied. Without a terminal and without `--accept-all`, a command that needs a prompt stops with exit 2 and says so, rather than waiting.
- A17. Stage modes of `install` (and any multi-stage command): fully automated is `--accept-all`; confirm by stage is the default and also available as `--confirm-stages`. Before each stage (install-prereqs, build, configure, then each start stage of `run`: emulators, trust, core, intelligence, health) it prints what the stage will do and asks `Run <stage>? [y]es, [n]o, [a]ll remaining`. `a` switches to automated for the rest of the run. `n` stops the run before that stage with exit 3 and a line saying what was done and what was not.
- A18 (revised 2026-11-15). Option `--bus-backend rabbitmq|emulator|azure` (default `rabbitmq`), stored in `<root>/.cynthus/settings.json` so `configure`, `run` and `rebuild` agree; a different value on a later command is refused unless `configure --force` is run. `emulator` and `azure` are the two Service Bus backends (F17): both set `SIGNAL_BROKER=servicebus` and both follow the owner's rule of seven (D7): only api, worker, scheduler, domain (core), auth (trust), analysis and chat (intelligence) hold a bus connection, and the core `.env` also gets `RECIPE_SIGNAL_BROKER=memory` (S9). The rule is also what keeps the emulator inside its limit of 10 connections (F5). Not chosen here: the owner said `--bus-backend azure`; `emulator` is my addition so that the Service Bus defaults the owner asked for have a local target. Say if you do not want it.
- A19 (revised 2026-11-15). `configure` sets Service Bus defaults when either Service Bus backend is chosen:
  - `emulator`: `SIGNAL_BROKER=servicebus`; `SERVICE_BUS_NAMESPACE=sb-cynthus-local`; `SERVICE_BUS_CONNECTION_STRING=Endpoint=sb://sb.cynthus.local;SharedAccessKeyName=RootManageSharedAccessKey;SharedAccessKey=SAS_KEY_VALUE;UseDevelopmentEmulator=true;` (the emulator's standard development string; not verified against the one JMac uses); `STORE_PASSWORD` generated (SQL Server password rules); `AZURE_USERNAME` and `AZURE_PASSWORD` empty; `RABBITMQ_URL` empty. `run` starts store, messaging and mail from cynthus-emulators and no RabbitMQ.
  - `azure`: `SIGNAL_BROKER=servicebus`; `SERVICE_BUS_NAMESPACE` from `--bus-namespace` or `CYNTHUS_BUS_NAMESPACE` (no default: the real namespace is not verified, F17); `SERVICE_BUS_CONNECTION_STRING` empty; `AZURE_USERNAME` and `AZURE_PASSWORD` from `CYNTHUS_AZURE_USERNAME` and `CYNTHUS_AZURE_PASSWORD` or a hidden prompt, and `AZURE_TENANT_ID` and `AZURE_CLIENT_ID` from the same kind of variables when given (whether the credential needs them is not verified). Alternatively `CYNTHUS_BUS_CONNECTION_STRING` (a connection string with a shared access key) replaces namespace and credentials. Secrets never come from command-line arguments (arguments show in process lists and logs); with `--accept-all` and a missing required value the command stops with exit 2 before anything starts. `run` starts only the mail sink from cynthus-emulators.
  - Both: topic `cynthus-events-topic`; each service's subscription names listed in the generated `<root>/.cynthus/bus-entities.txt`, compared with the emulator's `Config.json` (emulator) or printed for the owner to compare with Azure (azure). The script does not create Azure resources and does not edit cynthus-emulators; a missing subscription is reported by name (F17).
- A15. Real-machine test: the first system test is a full `install`, `test-full` and `remove` on the cynthus VM. It stops the VM's current stack, so it needs your explicit yes each time, like a deploy.

## Design

Package `cynthus-tools/cynthus_env/` (Python 3.11 or newer, standard library only; tests with pytest):

- `cli.py`: `main(argv)` with one subcommand per command above plus the common options `--root`, `--dry-run`, `--yes`, `--force`, `--timeout`; maps exceptions to exit codes of A12.
- `manifest.py`: `Manifest.load(path)`, `Repo` (frozen dataclass: `name`, `github`, `role`, `compose_dir`, `order`, `tests`), `ManifestError`.
- `prompt.py`: `Prompter(accept_all, interactive)` with `confirm(question) -> bool`, `confirm_stage(name, summary) -> StageAnswer` (yes, no, all); `NoTerminalError` (exit 2), `Declined` (exit 3). `cli.py` is the only place that builds it.
- `bus.py`: `BusBackend` (enum `rabbitmq`, `emulator`, `azure`), `bus_defaults(backend, secrets, options) -> dict` (A19), `bus_entities(manifest) -> list[str]`, `BUS_SERVICES` (the seven allowed to connect, by repository and compose service), `bus_env(backend, secrets) -> dict` per repository, `check_connected(rendered_configs) -> list[str]` (names of compose services whose rendered `SIGNAL_BROKER` is not `memory`); raises `BusSettingsError` (missing connection string, backend changed without `--force`).
- `runner.py`: `Runner` protocol with `run(args, cwd, env) -> Result`; `SubprocessRunner` and `RecordingRunner` (fake for tests, also used by `--dry-run`). No module runs a process any other way.
- `prereqs.py`: `install_prereqs(runner, distro)` with apt steps for git, python3, python3-venv, python3-pip, openssl, curl, Node 22, Docker Engine and the compose plugin (from Docker's apt repository); each step first checks whether it is already satisfied. Raises `UnsupportedPlatformError` outside Debian and Ubuntu.
- `repos.py`: `clone_all(manifest, root, runner)` and `update_all`, with `AccessError` when the SSH alias fails (D3); `ensure_base_image(runner)` (A6).
- `configure.py`: `configure(manifest, root, secrets, force)`, `Secrets` (read and create `secrets.env`), `render(template, values)`; raises `TemplateError` for a variable without a value.
- `stack.py`: `Stack` with `up(stage)`, `wait_healthy(stage, timeout)`, `stop()`, `down()`, `remove(confirm)`; `StageError` carries container name and log tail; `SafetyError` for A8 refusals.
- `tests_run.py`: `run_unit(manifest, root, runner)`, `run_integration(...)`, `run_system(...)`, `run_axe(...)` (A11).
- Files: `bin/cynthus-env`, `Makefile`, `cynthus_env/stack.json`, `cynthus_env/templates/<repo>.env.tmpl`.

Rules: only `runner.py` starts processes; `configure.py` knows nothing of Docker; `stack.py` knows nothing of tests; the manifest is the only place that names repositories.

## Acceptance criteria (testable)

- AC1 (unit). Each of the twelve commands exists, appears in `--help`, and with `--dry-run` runs no process (RecordingRunner records the commands, a test asserts none went to the subprocess runner). A test fails when a command is removed.
- AC2 (unit). `install-prereqs` on a fake Debian answers, in order, apt update, git, python3 and libs, openssl, Node 22, Docker and compose; with everything installed it runs no installer; on another distribution it raises `UnsupportedPlatformError` and exits 2.
- AC3 (feature integration). `build` against fake git (RecordingRunner) clones every manifest repository once into `--root`, updates with `--ff-only` on a second run, stops with `AccessError` and exit 2 when the SSH alias check fails, and stops with the pull error and exit 2 when the base image pull is refused (no fallback build).
- AC4 (unit). For every service repository, every `${VAR}` in its compose file without a default is a variable the template provides (test reads the compose files from a checkout given by an environment variable, skipped with a clear message in a plain tools checkout); a missing one fails the test.
- AC5 (unit). `configure` twice yields identical `.env` files and identical secrets; an existing `.env` is not overwritten without `--force`; secrets files have mode 600; no secret appears in the logs, the dry-run output or any file inside a repository clone other than its git-ignored `.env`.
- AC6 (feature integration). `run` starts stages in manifest order (emulators, trust, core, intelligence, health), waits for each stage to be healthy before the next, creates `cynthus_net` only if missing, and on an unhealthy container stops with `StageError` naming the container and exit 2. Fake runner.
- AC7 (unit). `stop` and `tear-down` visit repositories in reverse order, `tear-down` never passes `-v`, and no command other than `remove` passes `-v`, `--rmi` or deletes a directory (a test scans the recorded commands of every command).
- AC8 (CI-equivalent, tools tests). Each manifest `tests` command list is compared with the commands in the repository's `.github/workflows/ci.yml` `test` job when a checkout is available; a mismatch fails with both texts (guards against drift, F7).
- AC9 (unit). `remove` refuses without confirmation (a typed one, or `--accept-all`), refuses a root outside `--root`, `/` or a home folder, and refuses a clone with uncommitted or unpushed work unless `--force`; with confirmation it removes only manifest-owned containers, images, volumes and clones.
- AC10 (feature integration). `test` runs the manifest test commands for every repository that has them, in venvs, and exits 1 when any fails, 0 when all pass, and reports repositories without tests as "no tests", never as passed.
- AC11 (system integration, manual, with the owner's yes). On the cynthus VM: `install-prereqs`, `build`, `configure`, `run`, `test-full`, `stop`, `tear-down` and `remove` succeed in this order on a clean `--root`, `docker ps` shows every service healthy after `run`, and after `remove` no Cynthus container, image or volume of the manifest and no clone remains. Failures are reported with the failing step.
- AC12 (documentation). README, CHANGELOG, `docs/infrastructure.md` and the design document describe each command, the options, the exit codes (0 ok, 1 checks failed, 2 could not run, 3 declined), the options `--accept-all`, `--confirm-stages` and `--bus-backend`, the secrets file, what `remove` deletes and the step-1 requirement of D1.
- AC13 (lint). ruff and shellcheck clean on the new files; the script and tests need no network and no Docker.
- AC15 (unit). `Prompter` with `accept_all` answers yes and reads no input; without a terminal and without the flag a prompt raises `NoTerminalError` (exit 2); answer `a` in `confirm_stage` turns the rest of the run automated; answer `n` stops before that stage with exit 3 and a summary of done and not done; `--accept-all` does not pass a safety refusal of `remove` (dirty clone, bad root) and `--force` is a separate flag (tests for each).
- AC16 (feature integration). `install --accept-all` with a fake runner runs install-prereqs, build, configure and run in order with no prompt; `install` in default mode asks before each stage (including each start stage of `run`) and a scripted `y`, `y`, `a` answer sequence runs the rest unattended.
- AC17 (feature integration). With `--bus-backend emulator`, or `azure` with a fake namespace and credentials: the generated `.env` files for core, trust and intelligence have `SIGNAL_BROKER=servicebus` and the A19 values (emulator: namespace, connection string, generated `STORE_PASSWORD`; azure: namespace, credentials, empty connection string), the core `.env` has `RECIPE_SIGNAL_BROKER=memory`, and the rendered compose configuration of every service repository (`docker compose config`, skipped with a message when Docker's compose plugin is absent) has a non-`memory` `SIGNAL_BROKER` for exactly these services: api, worker, scheduler, domain, auth, analysis, chat. A service added to the compose files without a decision fails the test.
- AC18 (unit and feature integration). With `emulator`, `run` starts store, messaging and mail from cynthus-emulators and not RabbitMQ; with `azure` it starts only the mail sink; with `azure`, a missing namespace or credentials with `--accept-all` stops with exit 2 before any process starts; no secret (connection string, Azure password, store password) appears in any command line, log, dry-run output or repository file (test greps the recorded argument lists, log and output); changing the backend after `configure` without `--force` raises `BusSettingsError`.
- AC20 (unit). `bus_entities` lists the topic and one subscription per bus-connected service; for `emulator`, `run` compares the list with `Config.json` and reports each subscription the emulator lacks by name (exit 2 before starting the services), without editing the emulators repository.
- AC19 (CI, cynthus-core). The compose test of S9: with `RECIPE_SIGNAL_BROKER` unset every service's rendered `SIGNAL_BROKER` equals `${SIGNAL_BROKER}` as before; with it set only `recipe` changes.
- AC14 (accessibility). The command line has no colour-only output, prints plain text lines that a screen reader reads in order (one fact per line, results last), and the markdown docs follow the screen-reader rules (one h1, no pipe tables); a test checks the output format with `NO_COLOR` set and unset.

## Risks and unknowns

- R1. The base image pull depends on D5 (owner's statement, not verified). If the pull is refused on the VM, stop and report; do not add a fallback without the owner.
- R8. Azure: the namespace and its entities are outside the script (A19), and the credential form (`DefaultAzureCredential` with `AZURE_USERNAME` and `AZURE_PASSWORD`, plus possibly tenant and client id) is not verified; a wrong or missing entity shows as an unhealthy container. `recipe` on `memory` does not exchange signals with the other services (F15): the owner confirmed the list of seven; which web flows depend on recipe signals is not verified, so the first Azure run reports what stops working rather than assuming nothing does.
- R10. The emulator configuration lacks subscriptions for scheduler, worker and domain (F17); with `emulator` those services may fail to subscribe. AC20 reports it; the fix belongs in cynthus-emulators and is a separate issue, not part of this script.
- R9. A bad `--accept-all` run of `remove` deletes every manifest clone, image and volume without a question; the safety refusals (A8, A16) and the root checks are the only guard. The README says this in the first paragraph of the command's section.
- R2. The VM's stack is partly broken (F13); a first `run` may fail for reasons outside this script. S3's coder separates "script bug" from "stack bug" in the report and stops when a service fails to become healthy for a reason in its own code.
- R3. The six READMEs may not list every variable a compose file reads (AC4 will find them); the missing ones are added to the templates and noted in the issue, not guessed.
- R4. The `workflow_database` integration test needs the core database reachable from a container; if the compose network setup does not allow it, S5 reports and runs the mocked tests only.
- R5. Docker's apt repository and Node 22 are external; versions drift. The script prints the versions installed and the tools test pins nothing network related.
- R6. Compose files and CI jobs change; AC4 and AC8 exist to catch it, but manifest maintenance becomes a standing duty (documented in the README).
- R7. Overlap with axe S0 (A14): if S3 is not merged first, S0's coder must not start its own compose handling.

## Out of scope

- macOS with Colima and Windows with WSL2 (D2); a follow-up plan.
- Authentication with a token over HTTPS (D3 chose SSH); a follow-up if a machine has no SSH key.
- Production deployment, TLS, backup and restore of data volumes, upgrades of PostgreSQL major versions.
- Pulling a published release set instead of `dev` (needs the versioning scheme in design).
- Making cynthus-core, trust and others depend on this script; they keep their own README steps.
